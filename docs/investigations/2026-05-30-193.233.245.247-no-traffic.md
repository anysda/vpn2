# Расследование: «клиенты подключаются, но не получают трафик»

- **Дата:** 2026-05-30
- **Хост:** `193.233.245.247` (Ubuntu 24.04, `large-salmon.ptr.network`)
- **Симптом со слов пользователя:** клиенты подключаются по WireGuard, но не получают трафик — «только отправляют по wg»
- **Состояние сервера:** uptime 15 дней, последний деплой `/opt/anysda-vpn2` — коммит `6d72a4d` (6 дней назад)

## TL;DR

WireGuard на сервере **работает нормально** — handshake свежий, downlink (`server → client`) идёт гигабайтами, `tcpdump -i wg0` показывает живой двусторонний TCP. Симптом «трафика нет» **не подтверждается на сетевом уровне entry-ноды**.

Найдены 4 реальные проблемы, любая из которых может выглядеть для пользователя как «не работает»:

1. **`vpn.anysda.ru` указывает на старую entry** (`77.221.151.157`), а этот сервер обслуживает домен `vpn.anysda.space`. Если клиенты тянут конфиг/обновления с `vpn.anysda.ru` — они уходят на старый стенд.
2. **Два RU-CDN-IP недоступны c самого VPS** (TCP/443 timeout, ICMP timeout) — это `213.180.204.51` (Yandex CDN) и `91.197.193.223` (VK CDN). На них приходится **67 из 69 ошибок sing-box за сутки** → пользователи видят, что Yandex/VK-ресурсы не грузятся.
3. **GB-exit нестабилен** — за сутки 5 промахов `hy2-gb-direct` и серия переключений `selector` (`watchdog`).
4. **ICMP через VPN не работает** (ufw `Default: deny (routed)`) — клиенты не могут пинговать; TCP/UDP идёт, потому что перехватывается TPROXY до FORWARD-цепочки.

Расхождение между жалобой и фактом: пользователь, вероятно, наблюдает **(2)** на популярных RU-сайтах и **(1)** на самой панели; «трафик не идёт» — это субъективное обобщение.

## Wireguard wg0 — фактический трафик

```
peer-1   endpoint <RU мобильный>   handshake 13s ago    — десятки GiB downlink, активный
peer-2   endpoint <RU мобильный>   handshake 1m  ago    — десятки GiB downlink, активный
peer-3   endpoint <RU мобильный>   handshake 5h  ago    — отвалился
peer-4   endpoint <RU мобильный>   handshake 7h  ago    — отвалился
peer-5   (handshake не считан полностью)
```

Sent с сервера в сторону клиентов — десятки GiB на активный peer. Если бы клиент действительно не получал трафик, эта цифра не росла бы.

`tcpdump -i wg0` (12 сек, 30 пакетов): двусторонний TCP `<wg-client> ↔ <Google 443>` и `<Apple push 5223> ↔ <wg-client>`. Downlink работает.

## Маршрутизация (TPROXY)

Корректная PBR-схема под sing-box:
- `iptables -t mangle PREROUTING -i wg0 -j ANYSDA_WG_TPROXY` → `TPROXY ... mark 0x42 → 127.0.0.1:7898` (TCP+UDP), `RETURN` для `dst 10.99.0.1`.
- `ip rule 32765: from all fwmark 0x42 lookup 101`
- `ip route table 101: local default dev lo scope host` — пакеты возвращаются в локальный стек, sing-box их подбирает.
- `INPUT ACCEPT mark 0x42/0x42` — пропускает помеченные пакеты в локальный сокет.
- `sysctl: ip_forward=1, all.forwarding=1, wg0.forwarding=1` — OK.
- `rp_filter=2` (loose) — корректно для PBR.

`iptables -t mangle PREROUTING` счётчики: WG → TPROXY TCP 30M pkts / 6.1 GB; UDP 781K / 544 MB. Через TPROXY реально проходит трафик.

Топ ошибок sing-box за 24 часа (всего 69):

```
60  dial tcp 213.180.204.51:443: i/o timeout
 7  dial tcp 91.197.193.223:443: i/o timeout
 1  dial tcp 77.88.44.55:7
 1  dial tcp 192.168.1.100:8009
```

Воспроизведение **с самого сервера** (без VPN):
```
curl -m 8 -k https://213.180.204.51   → Connection timed out
curl -m 8 -k https://91.197.193.223   → Connection timed out
ping 213.180.204.51                   → 100% loss
ping 91.197.193.223                   → 100% loss
```

Контрольные RU-ресурсы:
```
ping ya.ru   (77.88.55.242)           → 7.6 ms OK
ping vk.com  (87.240.137.164)         → 10.6 ms OK
curl https://ya.ru (через enp0s3)     → HTTP/2 302 OK
```

**Вывод:** два конкретных IP заблокированы либо на стороне хостера (null-route/ACL), либо upstream-ом. Это не проблема vpn2 — лечится на стороне провайдера или маршрута через альтернативный uplink (например, через wgmgmt-mesh).

## Проблема (1): домен `vpn.anysda.ru` указывает не сюда

```
dig +short vpn.anysda.ru @1.1.1.1   → 77.221.151.157   (старая entry из config.yaml)
этот сервер                         → 193.233.245.247
caddy слушает домены                → vpn.anysda.space (см. /etc/caddy/Caddyfile)
```

В локальной `config.yaml` всё ещё:
```
panel:
  domain: vpn.anysda.ru
```

Если код панели / Telegram-бот / клиентские конфиги используют `vpn.anysda.ru` — они пойдут на 77.221.151.157, и поведение «не работает» зависит от того, что сейчас живёт на старой entry.

**Действие:** определиться, какой домен канонический — `vpn.anysda.ru` или `vpn.anysda.space`. Если переезжаем на `.space`:
- обновить `config.yaml` (`panel.domain: vpn.anysda.space`);
- DNS `vpn.anysda.ru` → перевести на `193.233.245.247` или поставить редирект.

## Проблема (3): GB-exit нестабилен

`anysda-failover-watchdog` за 24 часа:

```
5× hy2-gb-direct: промах (но до-проверка ожила — транзиент)
3× switch → hy2-gb-direct
2× switch → hy2-se-direct
1× switch → hy2-us-direct
1× switch → hy2-gb-warp
1× hy2-gb-warp: промах
```

Промахи bounce-ят между `gb-direct` и `gb-warp`, периодически весь узел GB уходит в штрафную (60–120с). На пользователя это пробрасывается как короткие 1–2-секундные «зависания» зарубежных запросов. Стоит проверить GB-exit отдельно (это `85.192.38.219` по `config.yaml`).

## Проблема (4): ICMP через VPN — `ufw deny (routed)`

```
ufw status verbose:
  Default: deny (incoming), allow (outgoing), deny (routed)
```

Никаких `route allow` правил для `wg0 → enp0s3` в ufw не объявлено. ICMP-форвард падает в FORWARD-цепочку `ufw-reject-forward`. С сервера:

```
ping 10.66.66.{2,3,5,6}   → 100% packet loss
```

TCP/UDP клиентов это **не** ломает, потому что TPROXY перехватывает пакеты в `mangle PREROUTING` ещё до FORWARD, и они идут в локальный сокет sing-box. Но любые сетевые диагностики вида «pinguju и не доходит» / `mtr` через VPN — не покажут ничего.

Если нужно чинить (опционально):
```
ufw route allow in on wg0 out on enp0s3
ufw route allow in on wg0
```

## Проблемы, которых нет (исключено)

- `ip_forward` выключен — нет, `=1`.
- NAT отсутствует — не нужен, схема TPROXY (трафик завершается локально и отправляется outbound от имени сервера).
- WG-handshake не завершается — handshake свежий у активных пиров.
- conntrack overflow — `count=908`, `max=65536`.
- Caddy упал — service active, ошибок нет.
- Sing-box не запущен — active, 6 дней непрерывно.

## Что нужно от пользователя

1. **Какой именно клиент жалуется** — endpoint IP (любой из: `62.217.184.254`, `109.252.96.223`, или другой)? Это позволит сузить с «вообще» до конкретного peer.

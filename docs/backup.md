# Резервные копии и восстановление

## Что в архиве

`./deploy.sh backup` снимает один зашифрованный архив всего, что нужно для
полного восстановления entry-ноды:

- `db.sqlite` панели (онлайн-копия через backup API SQLite, без простоя панели);
- секреты хранилища entry (токен бота, ключи S3, секреты панели и SSO,
  ключи ssh оркестратора и mgmt) - открытым JSON внутри
  зашифрованного архива; restore шифрует их ключом нового сервера, и новая
  entry входит на экзиты прежним ключом;
- `/etc/anysda/*`: clash-secret, telegram-runtime, manual-routes;
- серверный приватный ключ WireGuard (`/etc/wireguard/wg0.conf`) - без него
  клиентские `.conf` ломаются;
- OpenVPN CA + PKI (`/etc/openvpn/server/`: `pki/`, `server.conf`, `ccd/`, `crl.pem`) -
  без них ломаются существующие `.ovpn`;
- IKEv2 CA, серверный сертификат и ключ, конфиги swanctl (`/etc/strongswan`,
  `/etc/swanctl`);
- хранилище Caddy (`/var/lib/caddy/.local/share/caddy`: сертификаты, ключи,
  ACME-аккаунты);
- состояние деплоя (`/var/lib/anysda-vpn2/state/`): адреса mgmt-сети
  экзитов, список выключенных экзитов, манифест установленной сборки - без
  него новая entry раздала бы экзитам адреса заново;
- `manifest.json` с SHA-256 каждого компонента.

Архив шифруется [`age`](https://github.com/FiloSottile/age) открытым ключом
`/etc/anysda/backup.pub` на entry до записи на диск: открытый `.tar.gz` не
попадает ни в `/var/backups`, ни в S3. Закрытого ключа на entry нет: его
показывают один раз - мастер установки на экране «Бэкапы» или
`./deploy.sh -yaml` в конце вывода. `./deploy.sh restore` спрашивает его.

## Команды

```bash
./deploy.sh backup                    # снять архив сейчас
./deploy.sh backup-list               # список архивов
./deploy.sh restore                   # восстановить из latest
./deploy.sh restore <archive-name>    # из конкретного архива
./deploy.sh restore <archive> --force # перетереть непустую db.sqlite
```

Если база панели и конфиги VPN расходятся (не прошла выдача или отзыв
устройства), архив всё равно сохраняется: `./deploy.sh backup` завершается
успешно с предупреждением и номерами устройств, в «Событиях» панели -
«Бэкап сохранён с предупреждением». Эти устройства перевыпусти в панели.
Сбой бэкапа - ненулевой код выхода и «Бэкап не удался».

## Где хранятся

| Backend | Куда | Конфиг |
|---|---|---|
| `local` (default) | `/var/backups/anysda-vpn2/*.tar.gz.age` (chmod 700) | `backup.local.dir` |
| `s3` | `s3://<bucket>/<name>.tar.gz.age`, любой S3-совместимый endpoint | `backup.s3.*` |

Из `/var/backups/anysda-vpn2/` готовые `.tar.gz.age` может забирать внешний
агент (restic, borg, rsync). Снимки перед restore лежат в
`/var/backups/anysda-vpn2/.pre-restore/` и исключены из ротации.

Локальный бэкап - это откат, а не disaster recovery: авария в дата-центре
заберёт и entry, и её архивы. Для DR нужен внешний target: S3 у другого
провайдера или синхронизация на удалённое хранилище.

## Расписание и ротация

Раз в сутки с 02:00 по системному часовому поясу entry-ноды, случайная
задержка до 5 минут (`anysda-backup.timer`, `Persistent=true`: если нода была
выключена в 02:00, прогон случится после загрузки). Отключить -
`backup.schedule: off`. Сменить пояс:

```bash
ssh root@<entry> 'timedatectl set-timezone Europe/Moscow'
./deploy.sh 26-backup ru
```

Локально хранится `backup.retention` последних архивов (по умолчанию 10),
последний успешный не удаляется никогда. В S3 та же ротация применяется при
следующей выгрузке; дополнительно стоит поставить lifecycle policy на bucket.

## Конфигурация

```yaml
backup:
  enabled: true
  backend: local              # local | s3
  retention: 10
  schedule: daily             # off | daily
  local:
    dir: /var/backups/anysda-vpn2
  # s3:
  #   endpoint: https://s3.cloud.ru
  #   bucket: anysda-vpn2-backups
  #   region: ru-central-1    # обязателен: cloud.ru → ru-central-1,
  #                           # yandex → ru-central1, selectel → ru-1
secrets:
  # s3_access_key: ""
  # s3_secret_key: ""
```

Ключи S3 деплой переносит в хранилище секретов entry и стирает из
`config.yaml`. Обновление с 1.2.0 один раз показывает новый ключ вместе с
паролем архивов 1.2.0 и убирает пароль с entry: архивы, снятые до
обновления, restore открывает этим паролем, новые - ключом. Стадия
`26-backup` ставит `age`, `sqlite3` (и `rclone` при `backend: s3`) и
включает таймер.

## Что хранить вне entry

После деплоя в `config.yaml` секретов нет: они в зашифрованном хранилище
entry, копия которого на другой машине не открывается. Вне entry храните
`config.yaml`, ключ бэкапов (`AGE-SECRET-KEY-1…`) и ключи S3. Потерян
ключ - архивы, сделанные с ним, не расшифровать. Архивы 1.2.0 открывает
их прежний пароль.

## Восстановление entry-ноды с нуля

Нужны сохранённые вне entry `config.yaml` и ключ бэкапов, а при
`backup.backend: local` - ещё копия архива `.tar.gz.age`: локальные архивы
пропали вместе со старой entry, поэтому их заранее забирает внешний агент
(см. «Где хранятся»). При `s3` архив новая entry возьмёт из bucket сама.
Новая entry - чистая Ubuntu 26.04 с входом root, каким его выдал хостер.

```bash
# 1. свежая entry
ssh root@<новый-entry-ip>

# 2. репозиторий
git clone https://github.com/anysda/vpn2
cd vpn2

# 3. со своего компьютера: сохранённый config.yaml (при backend: local и архив)
scp config.yaml anysda-vpn2-<дата>.tar.gz.age root@<новый-entry-ip>:vpn2/

# 4. в config.yaml: entry.host - новый IP, если сменился; admin.ssh_pubkey -
#    свой открытый ключ ssh: без него restore на новом сервере откажет
#    (в config.yaml после обновления с 1.2.0 его нет - впишите).
#    При s3 в secrets: s3_access_key, s3_secret_key.
#    Временно panel.domain: "" и sso.enabled: false (SSO требует HTTPS):
#    деплой restore откроет панель по IP и не выпустит сертификат на домен
#    до восстановления архива
# 5. восстановить: секреты и ключи ssh прежней entry берутся из архива до
#    деплоя, экзиты пускают новую entry прежним ключом - строку
#    ./deploy.sh -key на экзиты класть не нужно; затем полный деплой и
#    restore архива. Ключ бэкапов restore спросит один раз, в начале, без
#    эха; без терминала читает его из stdin: < файл-с-ключом
#    backend: s3 - самый свежий архив или имя из ./deploy.sh backup-list
./deploy.sh restore latest
#    backend: local - путь к архиву, restore сам положит его в каталог
#    backup.local.dir (по умолчанию /var/backups/anysda-vpn2/)
./deploy.sh restore ./anysda-vpn2-<дата>.tar.gz.age

# 6. вернуть panel.domain и sso.enabled
./deploy.sh
```

Если на новой entry уже запускали `./deploy.sh -key`, ключ из архива
заменяет созданный: экзиты знают только ключ из архива, restore пишет об
этом строкой.

Экзиты не трогают и не переустанавливают. Новый entry получает новое
удостоверение аварийного режима, и `./deploy.sh` сам переводит на него
экзиты на стадии 23: их агенты забывают прежний entry и снимок клиентов
прежней установки, через минуту entry присылает новый снимок. Если экзиты
уже в аварийном режиме, потому что entry долго не было, deploy всё равно
проходит, а аварийный режим заканчивается на той же стадии: Hysteria2 и
панель экзита останавливаются сами. Restore на новой entry восстанавливает
архив сразу после своего деплоя: между ними аварийного доступа нет.

Restore сам пересобирает стадии 29/20/21/26/27/35/30 под восстановленные
секреты; пароль панели из архива имеет приоритет над
`secrets.admin_password` текущего `config.yaml`. Restore останавливает
Caddy и cert-sync, возвращает хранилище
с владельцем `caddy:caddy`, затем запускает службы. Сохранённый сертификат
должен подходить домену и оставаться действующим, иначе Caddy обратится к
ACME.

Клиенты переподключаются со своими старыми конфигами без перевыпуска
ключей. Если видны rejected handshakes - архив был снят до инициализации
ключей, клиентов придётся пересоздать. Если у entry сменился IP, а в
конфигах клиентов он прописан напрямую, им нужны свежие конфиги; с
`entry.public_host` (домен) хватит A-записи.

# anysda-vpn2

Самостоятельный VPN-сервис с веб-панелью: одна entry-нода в России, одна
или несколько exit-нод за рубежом, три протокола для клиентов (WireGuard,
OpenVPN, IKEv2), маршрутизация по географии, DNS с фильтрацией рекламы и
Telegram-бот. Ставится одной командой на чистые серверы.

> 🚀 **Сразу деплоить →** [Quickstart](#-quickstart--развернуть-с-нуля)

![Обзор](docs/screenshots/vpn2-overview.webp)

Обзор: события панели, трафик за сутки, нагрузка на экзиты, DNS с долей
блокировок. Ниже - карточки нод (CPU, iowait, RAM, статус), календарь
активности клиентов, топ клиентов по трафику и счётчики онлайн/офлайн.

![Клиенты](docs/screenshots/vpn2-clients.webp)

Клиенты и ключи: список с трафиком за сегодня, экзитом и сроком доступа,
фильтры «истекают» и «заморожены», рассылка от бота. Справа - карточка
клиента: срок, суммарный трафик, привязка к Telegram-боту, лимит устройств,
предпочитаемый экзит. Снизу - устройства с трафиком и кнопками: WG
(`.conf`/QR), OVPN (`.ovpn`), IKEv2 (сервер, Remote ID, короткий логин
вида `c1-d2` для ввода на телефоне, пароль и CA при работе без домена),
перевыпуск ключей, удаление; заморозка и удаление клиента.

## Возможности

- **Три протокола.** WireGuard, OpenVPN и IKEv2/IPsec на одной entry-ноде.
  IKEv2 работает штатными клиентами iOS, macOS, Windows и Android без
  сторонних приложений.
- **Клиенты и устройства.** Клиент - это человек, у него несколько
  устройств. У каждого устройства свои ключи WireGuard, сертификат OpenVPN
  и логин IKEv2. Лимит устройств, срок доступа, заморозка, перевыпуск
  ключей - из панели или из бота.
- **Маршрутизация по географии.** Российский трафик уходит напрямую с
  entry-ноды, зарубежный - через Hysteria2 на лучший экзит. Экзит падает -
  сторож переключает на другой за 10-14 секунд, живые соединения не
  рвутся. Режут UDP до экзита - канал уходит на запасной TCP (VLESS +
  Reality) и сам возвращается на Hysteria2, когда UDP оживает.
  Подробности: [docs/routing.md](docs/routing.md),
  [docs/failover.md](docs/failover.md).
- **Аварийный режим.** Пропала entry-нода целиком - через 20 минут
  экзиты сами поднимают запасной вход на Hysteria2, бот рассылает
  клиентам аварийные конфиги, администратору - адрес и пароль аварийной
  панели. Вернулась entry - клиенты переключаются обратно, аварийный
  доступ отключается сам. Подробности:
  [docs/emergency.md](docs/emergency.md).
- **Ручные правила.** Домен, IP или подсеть на конкретный экзит,
  перетаскиванием в панели. Применяется на ходу, без перезапуска и без
  обрыва соединений.
- **Предпочитаемый экзит клиента.** Весь зарубежный трафик клиента через
  выбранную страну. Экзит пропал - трафик временно идёт через общий выбор,
  вернулся - возвращается сам. Экзит удалён из установки - выбор клиента
  снимается, об этом строка в «Событиях» и сообщение в бот.
- **YouTube без рекламы (опционально).** YouTube выводится с российского
  адреса entry-ноды, где реклама не показывается, а блокировка DPI
  обходится десинхронизацией TLS (zapret2). Видеопоток проверяется каждые
  пять минут; если обход сломался, YouTube уходит на экзиты. Подробности:
  [docs/youtube.md](docs/youtube.md).
- **Локальная сеть не ломается.** Домашние адреса (RFC1918, CGNAT,
  multicast) не уезжают в туннель: роутер, NAS, принтер и Chromecast
  остаются доступны при поднятом VPN.
- **DNS с фильтрацией.** AdGuard Home для клиентов с включённой
  фильтрацией, управление - во вкладке «DNS» панели. Подробности:
  [docs/adguard.md](docs/adguard.md).
- **Telegram-бот.** Администратор управляет клиентами и получает алерты.
  Конечный клиент по ссылке-приглашению сам скачивает конфиги, добавляет
  устройства и видит уведомления.
- **Мониторинг.** Нагрузка нод, трафик за сутки, задержка до экзитов,
  активность клиентов - в панели. Журнал «События»: смена экзита, имени и
  лимита клиента, привязка к боту, маршрут YouTube; неудачные входы с
  одного адреса - одной строкой со счётчиком.
- **Резервные копии.** Один зашифрованный архив со всем нужным для
  восстановления entry-ноды, по расписанию, локально или в S3.
  Подробности: [docs/backup.md](docs/backup.md).
- **Вход в панель.** Один администратор, по желанию TOTP или SSO через
  OIDC-провайдера (проверено на Authentik): [docs/sso.md](docs/sso.md).

## Как это устроено

```
клиент WireGuard · OpenVPN · IKEv2
   │
   ▼
entry-нода (Россия)
 ├─ WireGuard / OpenVPN / strongSwan  →  sing-box (TPROXY)
 ├─ sing-box: ручные правила → YouTube → РФ напрямую → остальное на экзит
 ├─ сторож экзитов: пробы, переключение, балансировка
 ├─ zapret2: обход DPI для YouTube
 ├─ панель (Caddy, Let's Encrypt), AdGuard Home, VictoriaMetrics, бот
 │
 └─ Hysteria2 ──► exit-нода nl / fi / us / … ──► интернет
```

Exit-ноды связаны с entry-нодой туннелями Hysteria2 и служебной mgmt-сетью.
У каждого экзита два пути: прямой и через Cloudflare WARP. Полная схема
правил - [docs/routing.md](docs/routing.md).

**Стек.** Nuxt 4 (Vue 3, TypeScript) · Nuxt UI 4 · Drizzle ORM + SQLite ·
better-auth · sing-box · WireGuard · OpenVPN · strongSwan · AdGuard Home ·
VictoriaMetrics + node_exporter · Caddy · Ansible · Python
(`python-telegram-bot`).

**Структура репозитория.**

```
app/                 панель (Nuxt 4)
  shared/            данные, общие для панели, бота и деплоя
infra/
  ansible/           деплой: роль и плей на стадию, инвентарь из config.yaml
  vpn2/              пакет Python: логика на нодах и команда vpn2
  versions.yml       закреплённые версии внешних компонентов
  tests/             стенд и регрессии ролей и маршрутов
telegram/vpn2bot/    бот
deploy.sh            точка входа деплоя
config.example.yaml
docs/                инструкции и скриншоты
```

Как запускать тесты и где менять версии компонентов -
[Разработка и тесты](#разработка-и-тесты).

# 🚀 Quickstart — развернуть с нуля

Нужны: одна entry-нода в России и N exit-нод (минимум одна, лучше две-три
для отказоустойчивости). Чистая Ubuntu 26.04 на всех нодах и вход root по
SSH, каким его выдал хостер (пароль или ключ): он нужен только до
установки. Деплой запускается с entry-ноды, она же оркестратор. Как
подобрать серверы до оплаты - [docs/creation.md](docs/creation.md).

| Нода  | Минимум                 | Рекомендуется           |
|-------|-------------------------|-------------------------|
| entry | 1 vCPU, 2 ГБ RAM, 10 ГБ | 2 vCPU, 2 ГБ RAM, 20 ГБ |
| exit  | 1 vCPU, 1 ГБ RAM, 5 ГБ  | 1 vCPU, 2 ГБ RAM, 10 ГБ |

Entry-нода упирается в процессор: один vCPU занят полностью уже на
~120 Мбит/с суммарно. Лимиты служб подбираются по памяти; на машинах
меньше 4 ГБ деплой сам включает swap-файл до 2 ГБ.

**0. Домен (необязательно).** Направьте A-запись `vpn.example.com →
<entry-ip>` заранее: DNS расходится до четырёх часов, иначе Caddy не
получит сертификат при первом запуске. Только A-запись, без AAAA.

**Свой ключ ssh.** Деплой закрывает вход по паролю на всех нодах, дальше
вход только по ключу. Понадобится ваш открытый ключ: вывод
`cat ~/.ssh/id_ed25519.pub` на своём компьютере (файла нет - сначала
`ssh-keygen -t ed25519`).

**1. Зайти на entry-ноду и скачать исходники.**

```bash
ssh root@<entry-ip>
git clone https://github.com/anysda/vpn2
cd vpn2
```

Дальше один из двух способов. **В браузере** - мастер установки спросит
всё по экранам и проверит каждый экзит до установки: так проще всего в
первый раз. **По `config.yaml`** - всё заранее в файле, без браузера:
когда сразу нужны настройки, которых нет в мастере (порты, SSO, лимиты),
или установку повторяют. Ставится одно и то же, дальше настройки меняются
одинаково.

### Способ 1: в браузере

**2. Запустить мастер.**

```bash
./deploy.sh
```

Через минуту-другую (ставятся Caddy, Docker и сертификат на IP) он напечатает
ссылку и вернёт терминал:

```
  Откройте в браузере:  https://<entry-ip>/#<токен>

  Дальше в браузере; ссылка действует час, новая - ./deploy.sh
```

Ссылка действует час, открыть её можно в нескольких браузерах. Истекла
или потерялась - снова `./deploy.sh`: он напечатает новую, прежняя
перестанет работать. Введённое сохраняется на сервере, новая ссылка
откроет мастер с того же места. Во время установки `./deploy.sh` тоже
только выдаёт новую ссылку.

Если Let's Encrypt за минуту не выдал сертификат на IP, мастер работает на
самоподписанном, и под ссылкой будет строка:

```
  сертификат самоподписанный, отпечаток SHA-256 <отпечаток>
  браузер предупредит - сверьте отпечаток
```

Браузер предупредит о сертификате: откройте его сведения, сверьте
отпечаток SHA-256 с этой строкой и только тогда продолжайте.

**3. Экзиты и ключи.** На первом экране - строка ключа оркестратора и
кнопка «Копировать». Положите эту строку на каждый экзит:

```bash
ssh root@<exit-ip> "mkdir -p /root/.ssh && echo '<строка ключа>' >> /root/.ssh/authorized_keys"
```

Затем в форме: «Адрес» `root@<exit-ip>`, «Тег» - короткое имя экзита
(`de`, `nl`, `us2`), «Проверить». Годный сервер - «сервер годен: вход по
ключу есть, Ubuntu 26.04», тогда «Добавить». Так по каждому экзиту. Ниже
вставьте свой открытый ключ ssh и нажмите «Далее».

![Мастер: экзиты и ключи](docs/screenshots/vpn2-wizard-1.webp)

**4. Остальные экраны.** «Панель» - по IP сервера или свой домен, логин и
пароль администратора (придумайте). «Telegram-бот» - токен от @BotFather и
chat ID администратора, можно пропустить. «Бэкапы» - на этом сервере или
в S3; здесь же один раз показывается ключ бэкапов `AGE-SECRET-KEY-1…`:
сохраните его вне сервера, например в менеджере паролей, и отметьте «Я
сохранил ключ». «YouTube через РФ» - включить или нет. На экране
«Проверьте и установите» - «Установить».

![Мастер: ключ бэкапов](docs/screenshots/vpn2-wizard-4.webp)

**5. Установка.** Экран «Установка» показывает шаги и журнал текущего;
вкладку можно закрыть, ссылка вернёт сюда. Ошибка на шаге - «Повторить»
продолжит установку с того же места, «Продолжить без <ТЕГ>» - без
сломавшегося экзита (его можно добавить позже). В конце экран «Готово»
со списком систем и их состоянием и кнопка «Открыть панель». Вход в
панель - логином и паролем с экрана «Панель».

![Мастер: установка](docs/screenshots/vpn2-wizard-7.webp)

![Мастер: готово](docs/screenshots/vpn2-wizard-8.webp)

### Способ 2: по config.yaml

**2. Получить ключ оркестратора.**

```bash
./deploy.sh -key
```

Выведенную строку положите на каждый экзит:

```bash
ssh root@<exit-ip> "mkdir -p /root/.ssh && echo '<строка ключа>' >> /root/.ssh/authorized_keys"
```

**3. Заполнить конфиг.**

```bash
cp config.example.yaml config.yaml
nano config.yaml
```

Впишите `entry.host` (IP entry), `exits` (`tag` и `host: root@<exit-ip>`
на каждый экзит) и `admin.ssh_pubkey` (свой открытый ключ ssh).
Остальное необязательно, образец с комментариями -
[config.example.yaml](config.example.yaml).

**4. Запустить деплой.**

```bash
./deploy.sh -yaml
```

В конце вывода, один раз: пароль администратора панели (если он не задан
в `secrets.admin_password`) и ключ бэкапов. Сохраните оба вне сервера:
на диске их нет, второй раз они не покажутся.

```
Ключ бэкапов - показан один раз, на сервере его нет:
  AGE-SECRET-KEY-1…
Сохраните его вне сервера (менеджер паролей, бумага). ./deploy.sh restore спросит его.
```

Если Let's Encrypt не выдал сертификат, панель работает на самоподписанном,
и итог деплоя печатает строку «сертификат самоподписанный, отпечаток
SHA-256 …»: сверьте её с сертификатом в браузере.

### Как идёт деплой

Деплой сам скачивает манифест сборки ровно того commit, что лежит в
каталоге, и сверяет с ним хеши стадий и миграций, образов и загружаемых
компонентов; учётная запись GitHub не нужна. Затем ставит зависимости,
проверяет SSH ко всем нодам, поднимает mgmt-сеть и Hysteria2 на exit-нодах,
а на entry-ноде - VPN-серверы, роутер, сторож, AdGuard, мониторинг, панель
и бота. Повторный запуск безопасен: стадии идемпотентны.

Для своей работы деплой заводит на entry-ноде каталог `/opt/vpn2`:
виртуальное окружение Python с Ansible закреплённой версии и пакет `vpn2`.
Тот же пакет уезжает на exit-ноды. Ставить что-либо руками не нужно, в
системный Python ничего не попадает.

Состояние деплоя - адреса mgmt-сети экзитов, список выключенных экзитов,
манифест установленной сборки, ключи SSH нод - лежит в
`/var/lib/anysda-vpn2/state/`, а не в каталоге с исходниками. Каталог
`vpn2` можно удалить и скачать заново, установка этого не заметит.
Состояние входит в резервную копию.

Деплой на машине идёт один: второй запуск, пока работает первый, сразу
откажет. Перед изменениями деплой снимает на каждой ноде снимок базы, PKI и
конфигов и открывает журнал операции, удачный конец его закрывает. Если
деплой оборвался посреди изменений (Ctrl-C, обрыв SSH, перезагрузка),
следующий `./deploy.sh` откажет со строкой `незакрытый деплой на <нода>`:
проверьте службы и запустите `./deploy.sh recover` - полный повтор деплоя
поверх оборванного, - или `./deploy.sh rollback`.

Если сборка для свежего commit ещё идёт, deploy скажет об этом и ничего не
изменит: подождите 10-15 минут и запустите снова.

Если GitHub временно не отдаёт компонент (5xx, 429, обрыв), деплой повторяет
скачивание через 3, 10 и 30 с, затем берёт файл через API релизов GitHub;
хеш сверяется при любом пути. Не вышло и так - deploy назовёт компонент и
адрес: проверьте, что entry-нода видит github.com, и запустите снова.
Так же качает и `./deploy.sh --development`, хеш там закреплён в стадии.

Разовый сбой зеркала apt (5xx, 408, 429, обрыв) деплой тоже повторяет сам:
всего три попытки, через 5 и 10 с. Не помогло - строка «зеркало apt не
отдало <адрес> ...»: проверьте, что нода видит это зеркало, и запустите
снова. Ответ 404 и другие 4xx не повторяются.

На свежей ОС apt часто занят автообновлением. Полный деплой ставит
автообновления нод на паузу, через час они включаются сами. Идущее
обновление деплой не ждёт, а останавливает после текущего пакета: строка
«автообновление останавливается после текущего пакета».

Стадии, что меняют фаервол, идут под сторожем: если после правки на ноду
90 с не проходит новый вход по SSH, сторож возвращает правила, какими они
были до стадии. Вход для постановки сторожа сорвался - деплой повторяет
его до трёх раз через 5 с. Сторож так и не встал - строка `сторож
фаервола не встал` с нодой, кодом и выводом, стадия не запускается.

`./deploy.sh --development` — отдельный режим разработки: разрешает
плавающие теги и локальные правки без проверки сборки.

### Первый клиент

В панели «Новый клиент» → имя → в карточке клиента «+ девайс» → имя.
Дальше кнопки WG (`.conf` или QR), OVPN, IKEv2.

### Обновление

На entry, в каталоге `vpn2`:

```bash
git pull && ./deploy.sh
```

Обновление с 1.2.0 ничего не спрашивает. Ключ ssh, которым вы входите на
entry, остаётся; пароли root из `config.yaml` деплой убирает, секреты
переносит в хранилище entry. В конце один раз печатается новый ключ
бэкапов и пароль прежних архивов:

```
[deploy] пароли root entry и экзитов убраны из config.yaml: вход на серверы только по ключу
[deploy] секреты перенесены в зашифрованное хранилище entry и стёрты из config.yaml

Ключ бэкапов - показан один раз, на сервере его нет:
  AGE-SECRET-KEY-1…
Сохраните его вне сервера (менеджер паролей, бумага). ./deploy.sh restore спросит его.
Потеряете ключ - бэкапы не расшифровать: на сервере его нет, восстановить его нельзя.
Пароль архивов, сделанных до перехода на ключ: <пароль>
  Сохраните его рядом с ключом: restore таких архивов спросит его; на сервере его больше нет.
```

Сохраните оба: новые архивы открывает ключ, архивы до обновления - этот
пароль. Чтобы после обновления можно было восстановиться на новом
сервере, впишите в `config.yaml` `admin.ssh_pubkey` (свой открытый ключ
ssh): в конфиге 1.2.0 его нет, а `./deploy.sh restore` на новом сервере
без него откажет.

## Настройка

Всё задаётся в `config.yaml`, образец с комментариями -
[config.example.yaml](config.example.yaml). После правки конфига
перезапустите `./deploy.sh` целиком или нужную стадию, например
`./deploy.sh 30-frontend ru`.

### Порты и параметры клиентских VPN

```yaml
ports:
  wireguard: 51820      # UDP
  openvpn: 1194         # UDP или TCP
openvpn:
  proto: udp            # udp | tcp, с суффиксами 4/6
wireguard:
  mtu: 1420             # 1280..9000, MTU клиента и MSS сервера
  split_local: true     # обход локальных сетей клиента (WG и OpenVPN)
```

Применить: `./deploy.sh 28-wireguard ru`, `./deploy.sh 29-openvpn ru`,
`./deploy.sh 30-frontend ru`. После смены порта, протокола, MTU или обхода
локальных сетей клиентам нужно скачать конфиги заново, ключи перевыпускать
не нужно. Порт должен быть открыт во внешнем firewall хостера.

### Домен и IKEv2

Без домена панель доступна по `https://<entry-ip>/`: Caddy выпускает
сертификат Let's Encrypt на публичный IP с профилем `shortlived` (около
6 дней). Окно продления настроено на возраст сертификата 5 суток; для
домена — на оставшиеся 7 дней. ACME Renewal Information может назначить
более раннее обновление. TCP 80 должен быть доступен извне для HTTP-01,
TCP 443 — для панели; HTTP/3 выключен, UDP 443 остаётся VPN.

HTTP только перенаправляет на HTTPS. Пока сертификата от CA нет
(Let's Encrypt не ответил или исчерпан его лимит), панель работает на
самоподписанной паре, которая хранится на entry: браузер предупредит, а
итог deploy и `99-verify` печатают строку «сертификат самоподписанный,
отпечаток SHA-256 …» для сверки. Caddy повторяет попытки с
увеличивающейся паузой, таймер `vpn2-tls` раз в минуту видит новый
сертификат и подменяет пару перезагрузкой Caddy: панель не
перезапускается, вход не слетает. Сбой обновления не отключает
действующий HTTPS. Через настроенного бота администратор получает ошибку ACME и срок
сертификата, не чаще одного уведомления за 6 часов; после восстановления -
«TLS: обновлено». При недоступном боте сообщения сохраняются до доставки
(до 32 последних). Диагностика: `journalctl -u caddy -u vpn2-tls`,
`systemctl list-timers vpn2-tls`. Без настроенного Telegram-бота доступны
журнал и локальная очередь.

Укажите `panel.domain`, направьте A-запись и запустите `./deploy.sh`.
Caddy получит сертификат Let's Encrypt на домен. IKEv2 до
этого работает по IP со своим CA, после - автоматически переключается на
домен и доверие к Let's Encrypt: новым профилям CA ставить не нужно.
Профили IKEv2, выданные до подключения домена, продолжают работать:
сервер отвечает им прежним CA. Диагностика:
`journalctl -u anysda-ikev2-cert-sync -u caddy`.

### YouTube мимо экзитов

```yaml
youtube:
  route: zapret         # off | zapret | direct
  quic: block           # QUIC режется намеренно, десинк проверен на TCP
```

Проверка - только A/B, статус юнита ничего не доказывает:

```bash
ssh root@<entry> anysda-yt-check                    # 0 = обход живой
ssh root@<entry> 'journalctl -u anysda-yt-failover'  # журнал видеопробы
```

Если обход не проходит: `youtube.offload: off`, подобрать стратегию через
`/opt/zapret2/blockcheck2.sh` и записать в `youtube.strategy`, либо
`youtube.route: off`. Как это работает и что проверяет видеопроба -
[docs/youtube.md](docs/youtube.md).

### Сторож экзитов

Раз в две секунды сторож пробует каждый экзит. Три промаха подряд - экзит
считается мёртвым, новые соединения идут на другой, живые дорабатывают на
старом. Устройства разложены по 32 дорожкам, сторож держит каждую на
быстром экзите и выравнивает нагрузку. Экзит можно выключить вручную в
карточке экзита в панели. Если мертвы все каналы всех включённых экзитов
(с одним экзитом переключаться некуда), сторож перезапускает sing-box на
entry и пишет об этом в бот; настройка и выключение - ключи `failover.*`.
Пороги, балансировка, выход бота и перезапуск sing-box -
[docs/failover.md](docs/failover.md).

Стадии 20 (роутер) и 21 (сторож) обновляйте вместе:

```bash
./deploy.sh 20-ru-router ru && ./deploy.sh 21-failover-watchdog ru
```

### Отдельные стадии

```bash
./deploy.sh 30-frontend ru       # пересобрать панель
./deploy.sh 35-telegram ru       # перезапустить бота
./deploy.sh 10-foreign foreign   # все exit-ноды
./deploy.sh 19-yt-zapret ru      # обход DPI для YouTube
./deploy.sh 99-verify all        # проверка после деплоя
```

`99-verify` гоняет настоящий трафик через каждый протокол и экзит и
печатает строку на проверку. `✗` - отказ: деплой останавливается с кодом
1 и строкой `стадия 99-verify: одна или несколько нод завершились с
ошибкой`. `?` - не проверено (например, YouTube не дал измерить
видеопоток или WARP экзита молчит): установка годна, итог деплоя - «⚠
деплой завершён с предупреждениями» со списком таких строк, код выхода 2.

Полный список стадий и групп нод - `./deploy.sh --help`. Каждая стадия -
плей с её тегом в `infra/ansible/site.yml`, а что именно она делает на ноде,
описано в ролях `infra/ansible/roles/`. Стадия entry на экзите (и стадия
экзитов на entry) не запускается: `./deploy.sh 30-frontend se` - отказ.

### Обновление и откат панели

`git pull && ./deploy.sh` заменяет панель под защитой: новая версия
переносит базу на свою схему и должна ответить на проверку здоровья. Пока
идёт перенос, изменения из панели приостановлены, VPN продолжает работать.
Если новая панель не поднялась, деплой сам возвращает прежний образ.

Вернуть прежнюю панель вручную после удачного обновления:

```bash
./deploy.sh rollback
```

Откат меняет только образ панели. База, отзывы устройств, сроки доступа и
ключи остаются текущими, назад они не откатываются никогда. Поэтому откат
возможен, только если прежняя версия понимает нынешнюю схему базы; иначе
деплой откажет и предложит поставить совместимую сборку. Вернуть сами
данные - это `./deploy.sh restore` из резервной копии.

## Резервные копии

`./deploy.sh backup` снимает один зашифрованный архив со всем, что нужно
для восстановления entry-ноды: база панели, секреты `/etc/anysda`,
серверный ключ WireGuard, CA и PKI OpenVPN, сертификаты IKEv2, хранилище
Caddy. Архив шифруется [`age`](https://github.com/FiloSottile/age) до
записи на диск.

```bash
./deploy.sh backup                    # снять архив сейчас
./deploy.sh backup-list               # список архивов
./deploy.sh restore                   # восстановить последний (локально и в S3)
./deploy.sh restore latest --dry-run  # только показать, какой архив будет взят
./deploy.sh restore <archive> --force # перетереть непустую базу
```

По умолчанию архивы снимаются раз в сутки в 02:00 и хранятся в
`/var/backups/anysda-vpn2/` (последние 10). Для настоящего disaster
recovery архивы должны жить вне entry-ноды: S3 у другого провайдера или
синхронизация на удалённое хранилище.

Архивы шифруются открытым ключом. Закрытый ключ бэкапов показывается один
раз - на экране «Бэкапы» мастера или в конце `./deploy.sh` - и на сервере
не хранится. `./deploy.sh restore` спрашивает его без эха. Потерян ключ -
архивы, сделанные с ним, не расшифровать.

Вне entry храните ключ бэкапов, копию `config.yaml` и, при S3, ключи S3:
с ними entry восстанавливается на новом сервере.

Состав архива, хранение в S3, ротация и пошаговое восстановление entry-ноды
с нуля - [docs/backup.md](docs/backup.md). Что делать, когда умер экзит
или entry, - [docs/recovery.md](docs/recovery.md).

## Секреты

Пароли и ключи (токен бота, ключи S3, секрет SSO, ключи ssh оркестратора)
лежат в зашифрованном хранилище на entry, а не в `config.yaml`. Хранилище
открывается только на этой машине; в резервную копию оно входит.

Задать или сменить секрет - область `secrets:` в конце `config.yaml`:

```yaml
secrets:
  telegram_bot_token: 123456:ABC...
  s3_access_key:
  s3_secret_key:
  sso_client_secret:
  admin_password:
```

Пустое значение - секрет остаётся прежним. Вписанное значение применит
следующий `./deploy.sh` и сотрёт из файла:

```
[deploy] секреты перенесены в зашифрованное хранилище entry и стёрты из config.yaml
```

Пароль администратора не хранится нигде: `secrets.admin_password`
применяется к панели и стирается. Сменить его можно и в профиле панели.
Токен бота и секрет SSO можно вписать и в настройках панели.

## Экзиты

Экзиты добавляются и удаляются в панели: «Настройки» → «Экзиты».

![Экзиты в настройках](docs/screenshots/vpn2-settings-exits.webp)

**Добавить.** «Добавить экзит» показывает строку ключа оркестратора с
кнопкой «Копировать». Положите её на новый сервер (Ubuntu 26.04):

```bash
ssh root@<exit-ip> "mkdir -p /root/.ssh && echo '<строка ключа>' >> /root/.ssh/authorized_keys"
```

Затем «Адрес» `root@<exit-ip>`, «Тег», «Проверить» и «Установить». Ниже
идут шаги установки с журналом; экзит попадает в маршруты, мониторинг и
`config.yaml`, панель не перезапускается. Ошибка - «Повторить» продолжит
с того же места, «Забыть» уберёт то, что успело лечь.

![Добавление экзита](docs/screenshots/vpn2-settings-exits-add.webp)

**Удалить.** «Удалить» у экзита. Клиенты, закреплённые за ним, переходят на
авто. Итог задания говорит, что стало с сервером:

- «сервер очищен» - сервер ответил, наших служб и ключей на нём больше нет;
- «удалён и забыт» - сервер не ответил, на нём ничего не менялось: если он
  оживёт, ключ оркестратора и службы на нём остались.

Последний экзит удалить нельзя. Пока идёт `./deploy.sh` в терминале,
кнопки ждут его конца.

С entry на экзит по-прежнему ходит `ssh <тег>`.

## Telegram-бот

Опционален. Включается, если заданы `secrets.telegram_bot_token` и
`telegram.chat_id` (в `config.yaml` или в настройках панели). Админский чат -
личка с ботом или приватная группа с выключенным Group Privacy.

| Команда    | Что делает                                        |
|------------|---------------------------------------------------|
| `/clients` | список клиентов, создание, карточка с действиями  |
| `/status`  | состояние нод и задержка до экзитов               |

В карточке клиента: заморозить, лимит устройств, срок, приглашение,
удалить. «Отправить приглашение» даёт ссылку `t.me/<bot>?start=…` для
пересылки клиенту: по ней бот привязывает его чат, и дальше клиент сам
скачивает конфиги, добавляет устройства и получает уведомления об
изменениях. Ссылка привязывает один чат: открытая из другого Telegram, она
получает отказ. Привязка и отказ пишутся в «События». «Отозвать доступ к
боту» в панели отвязывает Telegram и делает старую ссылку
недействительной.

Бот не перевыпускает ключи, не трогает маршруты и не меняет свои
настройки - это только в панели.

## Разработка и тесты

Тесты на установку не влияют и для работы сервиса не нужны. Все команды -
из корня репозитория. Точный набор пакетов для каждого набора тестов - в
`.github/workflows/checks.yml`: CI запускает то же самое. Коммит, уже
проверенный на ветке, в `dev`, `main` и теге выпуска заново не проверяется.

```bash
# пакет vpn2: разбор config.yaml, бэкап, сторож, шаги стадий
pip install ./infra/vpn2 pytest pytest-xdist jinja2
python3 -m pytest infra/vpn2/tests -n auto --dist loadgroup

# регрессии ролей, маршрутов и sing-box; сетевые - только с бинарником
# sing-box и правом на netns, без них пропускаются
SING_BOX_BIN=/path/to/sing-box RUN_NETNS_TESTS=1 python3 infra/tests/run_parallel.py

# бот
pip install -r telegram/requirements.txt
python3 infra/tests/run_parallel.py --dir telegram/tests

# роли и плеи Ansible
pip install -c infra/ansible/constraints.txt ansible-core mitogen ansible-lint
export ANSIBLE_CONFIG=infra/ansible/ansible.cfg
ansible-lint --profile production --offline --project-dir infra/ansible \
  infra/ansible/site.yml infra/ansible/roles

# панель: линт, типы, unit-тесты (vitest), сквозные тесты (Playwright)
cd app && pnpm install
pnpm lint && pnpm typecheck
pnpm test:unit
pnpm e2e:local
```

Сквозным тестам панели нужен Docker: `pnpm e2e:local` сам собирает образ
панели и поднимает её с подставными VPN-службами. Эталонные снимки экранов
(`app/e2e/screenshots.spec.ts`) в обычный прогон не входят и сверяются
отдельно: кнопкой запуска `shots.yml` или пушем в ветку `shots/<имя>`.

**Стенд.** Полная установка проверяется на двух виртуальных машинах под
KVM, entry и экзит, на Ubuntu 24.04 и 26.04: штатный `./deploy.sh` с
entry-ноды, затем `99-verify` с настоящим трафиком WireGuard, OpenVPN и
IKEv2, повторный деплой без изменений и восстановление из архива. Отдельно
проверяются обновление с прошлого выпуска (на `lane/release` - с 1.1.5) и
обрыв UDP до экзита. В CI это `stand.yml` на каждый пуш в `dev` и в ветку
выпуска `lane/release`; коммит, пройденный на `lane/release`, в `dev` не
повторяется. Локально, на машине с KVM:

```bash
sudo infra/tests/ci-stand.sh up
sudo infra/tests/ci-stand.sh deploy <образ панели>
sudo infra/tests/ci-stand.sh verify
sudo infra/tests/ci-stand.sh down
```

Остальные сценарии стенда перечислены в начале `infra/tests/ci-stand.sh`.

**Версии компонентов.** Версии и контрольные суммы всего, что деплой
скачивает со стороны (sing-box, AdGuard Home, Caddy, VictoriaMetrics,
zapret2, Ansible и другие), записаны в одном файле `infra/versions.yml`.
Обновить компонент - поменять строку там; при обычном `./deploy.sh`
скачанное сверяется с манифестом сборки этого commit.

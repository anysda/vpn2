# Сторож экзитов

`infra/lib/failover-watchdog.py`, ставится стадией `21-failover-watchdog`.
Настройки в `/etc/anysda/failover-watchdog.env` переживают передеплой; битое
значение заменяется умолчанием. Адрес и секрет clash-api стадия 21 пишет
заново.

## Переключение без обрыва

`interrupt_exist_connections: false` на всех группах sing-box
(`direct-best`, `warp-best`, `foreign-best`). Переключение на новый экзит
берёт только новые соединения; живые, в том числе идущая загрузка,
дорабатывают на старом. Раньше каждое переключение рвало всё сразу: при 63
переключениях за 7 дней это било по всем клиентам, а не только по тем, чей
экзит правда умер.

## Пороги

`INTERVAL=2`, `PROBE_TIMEOUT_MS=3000`, `DEAD_AFTER=3` отсекают короткие
всплески. Цена - настоящий простой экзита клиент видит 10-14 с: до 2 с
ожидания тика, первый промах по таймауту 3 с, ещё две до-проверки по 0,4 +
3 с, и лишь потом переключение; дальше клиенту нужно открыть новое
соединение.

Возврата на «первый» экзит нет: после восстановления старый экзит снова
выбирается, только если он быстрее текущего больше чем на `TOLERANCE_MS`
(120 мс) `LATENCY_HOLD` тиков подряд. Выбор сторожа хранится в
`/var/lib/sing-box/cache.db` и переживает перезапуск sing-box.

Журнал пишет причину каждого промаха зонда: `таймаут`, `отказ соединения`,
`код <N>` или текст исключения.

## Ручное выключение экзита

Переключатель в карточке экзита в панели (`PATCH /api/ops/exits/:tag`)
пишет `/etc/anysda/exits-disabled.json`; сторож обходит выключенный узел как
мёртвый: уводит выбор сразу и рвёт его соединения (кроме mgmt). Последний
включённый экзит выключить нельзя.

## Балансировка по дорожкам

`BALANCE=on|off`, по умолчанию `on`; выставленное на узле `off` переживает
передеплой. Клиентские устройства разложены по 32 селекторам `lane-NN` по
VPN-IP (октет mod 32). Сторож держит каждую дорожку на быстром экзите
(EWMA-задержка ≤ лучшей + 150 мс; медленным узел считается после 60 с
подряд). Переезды - при смерти или выключении узла (сразу), при дисбалансе
> 35 % и > 5 Мбит/с (раз в 5 мин, по одной дорожке, не чаще раза в 30 мин
на дорожку); спящие дорожки без соединений выравниваются тихо. `BALANCE=off`
- дорожки повторяют `foreign-best`. Переехавшее устройство получает другой
внешний IP для новых соединений.

Дорожка, ушедшая на WARP своего узла из-за смерти direct (например, деплой
перезапустил sing-box на экзите), возвращается на direct, когда тот жив без
перерыва `WARP_RETURN_S` (10 мин), не дожидаясь 30-минутной стоянки. Если
дорожка уже возвращалась с WARP меньше 30 мин назад (direct мигает),
следующий возврат ждёт полную стоянку.

## Выход бота

Отдельная группа `tg-best`, через неё ходит весь трафик прокси бота. Bot API
(`api.telegram.org`) режут не на всех экзитах, а gstatic-проба этого не
видит. Раз в `TG_INTERVAL_S` (30 с) сторож проверяет Bot API через текущий
выход бота; после `DEAD_AFTER` промахов подряд, или сразу при ручном
выключении узла, переводит бота на экзит, где Bot API отвечает. Если Bot API
молчит везде, поиск повторяется раз в 30 с.

## Перезапуск sing-box

С одним экзитом переключаться некуда, и канал, залипший в sing-box на entry,
лежал бы до ручного перезапуска. Поэтому, если у всех включённых узлов мертвы
все каналы (direct и warp) `restart_after_checks` проверок подряд, сторож
делает `systemctl restart sing-box`, пишет об этом в журнал и шлёт событие
«Экзиты» в бот. Жив хоть один канал - счётчик с нуля. Узел, выключенный
вручную, в проверку не входит, а если он сам жив, перезапуска нет: sing-box
везёт. Выключены все узлы - перезапуска тоже нет. Штрафная скамья на проверку
не влияет: опрашиваются все включённые узлы. Не ответил clash-api на
запрос группы - проверки не было, счётчик стоит. Группа ответила, а пробы
упёрлись в отказ соединения - это молчит clash-api, а не каналы: счётчик с
нуля.

Ключи в `config.yaml`, блок `failover:`:

- `restart_after_checks` - проверок подряд до перезапуска, по умолчанию 3;
  `0` выключает перезапуск.
- `restart_min_interval` - перезапуск не чаще раза в столько секунд, по
  умолчанию 600.

Сколько длится проверка. Сторож опрашивает все каналы разом и ждёт
самого медленного, потом спит `INTERVAL` (2 с). Живые каналы отвечают за свою
задержку, и проверка занимает около 2 с. Мёртвый канал держит пробу до
`PROBE_TIMEOUT_MS` (стадия ставит 3000 мс), но не дольше 4 с, поэтому при
мёртвых каналах проверка длится 5-6 с. Есть выключенные узлы - их
опрашивают вторым кругом, ещё до 4 с, и проверка растягивается до 10 с. При
умолчании 3 перезапуск наступает примерно через 13-16 с от начала первой
неудачной проверки, с выключенными узлами через 22-28 с.

Блок пишется только с отступами, строку вида `failover: {...}` config2env
отвергает; значения - целые числа ≥ 0:

```yaml
failover:
  restart_after_checks: 3
  restart_min_interval: 600
```

Эти два ключа живут только в `config.yaml`: нет ключа - действует умолчание,
прошлое значение из `/etc/anysda/failover-watchdog.env` не сохраняется. После
правки:

```bash
./deploy.sh 21-failover-watchdog ru
```

Где смотреть: журнал сторожа (`journalctl -u anysda-failover-watchdog`),
строки с «перезапускаю sing-box» и «sing-box не перезапустился». Время
последнего перезапуска лежит в `/var/lib/anysda-failover-watchdog/restart.json`,
поэтому предел частоты переживает перезапуск самого сторожа.

## Стадии 20 и 21 обновлять вместе

Группы `tg-best` и `pin-*` создаёт стадия 20 (роутер), а ведёт их сторож из
стадии 21. Новый конфиг со старым сторожем оставит бота на первом попавшемся
экзите, а ручные маршруты без запасного; новый сторож со старым конфигом не
найдёт, чем управлять.

```bash
./deploy.sh 20-ru-router ru && ./deploy.sh 21-failover-watchdog ru
```

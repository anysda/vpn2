# Маршрутизация на entry-ноде

Как sing-box на entry-ноде решает, куда уходит каждое соединение, и какие
ограничения из этого следуют.

## Порядок правил

```
WireGuard client  ·  OpenVPN client  ·  IKEv2 client
   │ wg0 udp/51820        tun0 udp/1194    udp/500 IKE + udp/4500 ESP/NAT-T
   ▼
[entry-нода]
 ├─ WireGuard (wg0) + OpenVPN (tun0) + strongSwan (xfrm0)
 │   iptables PREROUTING -i wg0/tun0/xfrm0 → TPROXY → sing-box :7898
 ├─ sing-box роутер
 │   служебные правила (скрейп экзитов, блок loopback, бот)
 │   ручные правила панели → /etc/sing-box/manual-routes/ (набор на экзит)
 │   предпочитаемый экзит клиента → /etc/sing-box/client-prefs/ (набор на узел)
 │   YouTube → youtube-ru (WAN entry, РФ-IP) + метка → nfqws2-десинк
 │   geoip:ru / .ru/.рф → direct-ru (WAN entry)
 │   клиентский VPN-IP → lane-00..31 (дорожки, экзит каждой выбирает сторож)
 │   остальное → foreign-best (hy2-* экзиты; выбирает сторож)
 ├─ nfqws2 (zapret2) — обход DPI для YouTube, только помеченный трафик
 ├─ панель (Caddy → :51821), AdGuard Home, VictoriaMetrics, бот
 └─ hy2-{tag}-direct / hy2-{tag}-warp → exit-нода → интернет
```

Ручные маршруты стоят сразу за служебными правилами и выше всех остальных;
из пересекающихся побеждает верхний в панели. Правка маршрута применяется
на ходу: sing-box перечитывает наборы правил сам, соединения не рвутся.
Перезапуск sing-box нужен только когда передеплой меняет состав экзитов.

## Ручные правила и предпочитаемый экзит

Ручной маршрут панели на конкретный экзит не рвётся, когда экзит пропадает:
пока узел выключен, мёртв или в штрафной после падения, трафик маршрута идёт
через `foreign-best`, а потом возвращается на выбранный экзит (группы
`pin-<экзит>`). Когда экзит возвращается, соединения маршрута, открытые за
это время через `foreign-best`, закрываются, и клиенты переподключаются уже
через экзит.

Предпочитаемый экзит клиента - флаг в карточке клиента (🌐 - авто).
Зарубежный трафик всех устройств клиента идёт через выбранный экзит вместо
дорожек; РФ, YouTube и ручные маршруты - как обычно. Отказоустойчивость та
же, что у ручных маршрутов: через группу `pin-hy2-<узел>-direct`. Панель
пишет IP устройств в `/etc/anysda/client-prefs.json`, роутер раскладывает их
по наборам правил, смена экзита применяется без обрыва соединений.

У каждого устройства постоянный адрес во всех трёх протоколах: WireGuard из
`wg0.conf`, OpenVPN через ccd (`ifconfig-push`), IKEv2 из пула в один адрес
на устройство.

## Сплит-туннель по локальным сетям

По умолчанию включён. RFC1918, CGNAT (`100.64/10`) и multicast не уезжают в
VPN - роутер, NAS, принтер, Chromecast и docker-сети остаются доступны при
поднятом туннеле. В WG это дополнение `0.0.0.0/0` в `AllowedIPs` (с дыркой
под endpoint, иначе wg-quick ловит петлю), в OpenVPN - `route … net_gateway`.
Выключается `wireguard.split_local: false` в `config.yaml`, код -
`app/server/utils/allowed-ips.ts`.

## IPv6: ULA fast-fail для WireGuard

`AllowedIPs` пропускает клиента в `2000::/3`, чтобы v6 не утёк мимо VPN к
оператору, но v6-адреса на туннельных интерфейсах нет. Раньше пакет уходил
в туннель и там молча пропадал: клиент ждал таймаут, у Telegram на IPv6-only
сотовых сетях падало каждое третье соединение. Теперь у клиента и у entry-ноды
есть парный ULA-адрес `fd66:66::N/64` (N тот же, что в `10.66.66.N`), а
entry отвечает на любой v6 с `wg0` мгновенным ICMPv6 `destination
unreachable`: приложение получает отказ за один RTT и тут же берёт v4.
Старым клиентам нужно перекачать `.conf`/QR: ULA-адрес прописывается только
в свежем конфиге.

## Ping из VPN не работает

Внешний IPv4 ping у WG, OpenVPN и IKEv2 сразу получает от entry
`Destination Protocol Unreachable` (ICMP type 3/code 2). Это ограничение
транспорта, а не признак недоступности адреса:
[Hysteria2](https://v2.hysteria.network/docs/developers/Protocol/#proxy-requests)
переносит только TCP/UDP, в закреплённом
[sing-box 1.12.25](https://github.com/SagerNet/sing-box/blob/v1.12.25/protocol/hysteria2/outbound.go#L89-L101)
другие сети отклоняются. Отказ действует и для IP экзита, и для адресов,
которые TCP/UDP-правила направляют напрямую. Ответы удалённых адресов не
имитируются, ICMP не уходит с IP entry в обход выбранного экзита. Ping
собственных адресов entry остаётся локальным и проверяет только туннель до
entry. ICMP-ошибки и PMTU этим правилом не блокируются.

Для проверки внешнего пути используйте HTTP(S): `curl -4 https://api.ipify.org`.
Правило видно в `iptables -S FORWARD` по комментарию `vpn2: Hysteria2 has
no ICMP`. Настоящий ping через экзит потребовал бы отдельного IP-туннеля
entry-exit и согласования его маршрутов с sing-box.

## QUIC (UDP/443)

tproxy-вход сниффит домен, но не подменяет им назначение
(`sniff_override_destination` выключен). С подменой назначение UDP-потока
становилось доменом, tproxy не мог отправить ответ с адреса-источника,
равного назначению, и QUIC-хендшейк молча умирал; правила по IP и подсети из
панели и `geoip: ru` не видели исходного адреса. Без подмены назначение - тот
IP, куда шёл клиент: ответ уходит с него, правила по IP матчатся. Правила по
домену матчат сниффнутый домен из метаданных соединения и подмены не требуют.

## Telegram с маскировкой SNI

При блокировке Telegram ходит на свои IP с чужим SNI, вплоть до `*.ru`.
IP Telegram исключены из правила `.ru → direct-ru`, иначе такие соединения
уходили бы в Telegram с российского адреса.
